# Implementation

## Overview

The reactive jammer is implemented through a combination of a custom application module and extensions to the IEEE 802.11p physical layer of **VEINS 5.3.1**.

The design follows a PHY-assisted reactive jamming approach:

- the **application layer** (`JammerApplication`) is responsible for controlling the attack logic, maintaining the jammer state, and deciding when to start and stop a jamming burst;
- the **PHY layer** (`PhyLayer80211p`) is responsible for generating the actual interference signal and injecting it into the wireless channel;
- the **base PHY layer** (`BasePhyLayer`) is extended with a notification mechanism that informs the jammer whenever a legitimate wireless transmission starts reception.

This approach avoids modifying the MAC protocol while allowing the jammer to react directly to physical channel activity.

The implementation is divided into the following components:

| File | Purpose |
| ----------------------- | ----------------------------------------------------------------------------- |
| `JammerScenario.ned` | Extends the original VEINS scenario by adding a jammer RSU node. |
| `JammerApplication.ned` | Defines the jammer application module and configurable parameters. |
| `JammerApplication.h` | Declares jammer variables, timers, and PHY-layer references. |
| `JammerApplication.cc` | Implements transmission detection, jammer state control, and attack scheduling. |
| `BasePhyLayer.cc` | Adds the `incomingFrame` PHY notification mechanism. |
| `PhyLayer80211p.cc` | Implements the generation and transmission of artificial interference signals. |
| `omnetpp.ini` | Defines jammer parameters and simulation configurations. |

The implementation keeps the original VEINS architecture unchanged except for the additional PHY-layer functionality required for reactive jamming.

---

# Jammer Architecture

The jammer is deployed as a stationary RSU using the standard VEINS IEEE 802.11p communication stack, accessing the PHY layer to create an artificial wireless signal.

The operation is divided into three stages:

1. **Detection**
   
   The PHY layer detects the arrival of a legitimate IEEE 802.11p transmission and generates an internal notification.

2. **Decision**

   The jammer application receives the notification and decides whether a jamming burst should be activated.

3. **Interference Generation**

   The PHY layer creates an artificial IEEE 802.11p frame containing a high-power signal and injects it into the wireless channel.

# BasePhyLayer Extension

## Incoming Frame Notification

The standard VEINS `BasePhyLayer.cc` does not expose incoming transmissions to upper modules. To allow reactive detection, an additional OMNeT++ signal was introduced.

A new signal identifier was added:

```cpp
simsignal_t sigIncomingFrame;
````

This signal represents the beginning of a PHY-layer reception event.

During initialization, the signal is registered:

```cpp
sigIncomingFrame = registerSignal("incomingFrame");
```

The registration is performed during stage 0 of the PHY initialization process.

---

## Detecting Legitimate Transmissions

The notification is generated inside:

```cpp
BasePhyLayer::handleAirFrameStartReceive()
```

which is executed whenever a new `AirFrame` arrives from the wireless channel.

The original function was extended with:

```cpp
if (frame->getProtocolId() != PROTOCOL_ID_JAMMER) {
    emit(sigIncomingFrame, frame);
}
```

Before emitting the notification, the PHY layer checks the protocol identifier of the received frame.

A new protocol identifier was introduced:

```cpp
enum ProtocolIds {
    PROTOCOL_ID_GENERIC = 0,
    PROTOCOL_ID_JAMMER = 9999
};
```

Frames generated by the jammer use `PROTOCOL_ID_JAMMER`. These frames are ignored by the jammer to prevent self-triggering.

Without this filtering mechanism, every jamming burst would immediately trigger another jamming event, causing continuous interference.

The resulting behaviour is:

* legitimate IEEE 802.11p frames → notification generated;
* jammer-generated frames → ignored by the jammer.

After the notification step, the normal VEINS reception process continues:

```cpp
channelInfo.addAirFrame(frame, simTime());
```

Therefore, the modification does not affect standard packet reception.

# JammerApplication Implementation

The jammer application is implemented in ```JammerApplication.cc``` and extends the VEINS ```DemoBaseApplLayer```.

The application is responsible for controlling the attack process but does not directly generate wireless signals.

---

## Initialization

During initialization, the application loads the jammer parameters from `omnetpp.ini`:

```cpp
jammingDuration = par("jammingDuration").doubleValue();
jammingPower = par("jammingPower").doubleValue();
jamChannel = par("jamChannel").intValue();
enabled = par("enabled").boolValue();
```

The parameters define:

| Parameter         | Description                                    |
| ----------------- | ---------------------------------------------- |
| `enabled`         | Enables or disables the jammer.                |
| `jammingDuration` | Duration of each interference burst.           |
| `jammingPower`    | Transmission power of the interference signal. |
| `jamChannel`      | IEEE 802.11p channel used for jamming.         |

A self-message timer is created:

```cpp
jamStop = new cMessage("jamStop");
```

This timer controls the end of each jamming transmission.

---

## Accessing the PHY Layer

The jammer requires direct access to the physical layer.

First, the application obtains the local NIC (Network Interface Card) module.

The NIC is the VEINS component that represents the vehicle/RSU wireless communication hardware, containing the IEEE 802.11p protocol stack modules (MAC and PHY) responsible for packet transmission, reception, and wireless channel interaction.

```cpp
cModule *nic = getParentModule()->getSubmodule("nic");
```

Then it retrieves the IEEE 802.11p PHY module:

```cpp
phy = dynamic_cast<PhyLayer80211p*>(
        nic->getSubmodule("phy80211p"));
```

The PHY reference is required because the interference signal is not created as a normal application packet.

Instead, the application calls a dedicated PHY function:

```cpp
phy->startJamming(...)
```

which creates and transmits the interference signal.

---

# PHY Signal Subscription

After obtaining the PHY module, the jammer subscribes to the custom signal:

```cpp
phy->subscribe("incomingFrame", this);
```

From this point, the application receives a callback whenever the PHY layer detects a legitimate incoming transmission.

The jammer therefore remains idle during periods of channel inactivity.

---

# Reactive Detection Process

When a transmission starts reception, OMNeT++ invokes:

```cpp
JammerApplication::receiveSignal()
```

The first check ensures that the signal comes from the expected PHY module:

```cpp
if (source != phy) {
    return;
}
```

This prevents unrelated simulation signals from activating the jammer.

The application then verifies the jammer state:

```cpp
if (!enabled || isJamming)
    return;
```

A new attack is started only when:

* the jammer is enabled;
* another jamming burst is not already active.

If the conditions are satisfied:

```cpp
startJamming();
```

is executed.

---

# Starting a Jamming Burst

The function:

```cpp
JammerApplication::startJamming()
```

changes the internal state:

```cpp
isJamming = true;
```

and requests the PHY layer to generate interference:

```cpp
phy->startJamming(
    SimTime(jammingDuration),
    jammingPower,
    jamChannel
);
```

The application does not create frames itself. The PHY layer performs all operations required for transmission.

After activation, a timer is scheduled:

```cpp
scheduleAt(
    simTime() + jammingDuration,
    jamStop);
```

When the timer expires, the jammer returns to the idle state.

---

# Ending a Jamming Burst

The timer event is handled in:

```cpp
handleSelfMsg()
```

When the received message is:

```cpp
jamStop
```

the function:

```cpp
stopJamming();
```

is executed.

The jammer state is reset:

```cpp
isJamming = false;
```

The node can now react to the next legitimate transmission.

---

# PHY-Layer Jamming Generation

The physical interference generation is implemented inside ```PhyLayer80211p.cc```:

```cpp
PhyLayer80211p::startJamming()
```

The PHY layer creates an artificial AirFrame carrying a high-power interference signal. The frame structure is only used to inject energy into the VEINS channel model and does not represent a valid application transmission.

---

## Creating the Artificial MAC Frame

A temporary MAC packet is created:

```cpp
auto macPkt =
    new Mac80211Pkt("JammerMacPkt", 0);
```

The packet does not contain meaningful application data. Its purpose is only to provide the structure required by VEINS to create an `AirFrame`.

The addresses are set to zero:

```cpp
macPkt->setDestAddr(0);
macPkt->setSrcAddr(0);
```

because the packet is not intended for successful delivery.

---

## Creating the AirFrame

The packet is encapsulated into an air frame:

```cpp
auto frame = createAirFrame(macPkt);
frame->encapsulate(macPkt);
```

The frame is configured as an IEEE 802.11p transmission:

```cpp
frame->setProtocolId(IEEE_80211);
frame->setChannel(channel);
frame->setKind(AIR_FRAME);
```

The IEEE 802.11 protocol identifier is important because it allows the normal VEINS PHY reception and interference mechanisms to process the transmission.

---

## Configuring the Point of Attachment

Before transmission, the frame receives antenna and position information:

```cpp
AntennaPosition pos = antennaPosition;
Coord orient = antennaHeading.toCoord();

frame->setPoa({pos, orient, antenna});
```

The Point of Attachment (POA) contains:

* jammer position;
* antenna orientation;
* antenna model.

The POA is required by `BasePhyLayer::filterSignal()` to calculate antenna gain and propagation effects.

Without this information, the signal would not correctly interact with the VEINS channel model.

---

# Creating the Jamming Signal

The interference signal is represented using the VEINS `Signal` class:

```cpp
Signal signal(
    overallSpectrum,
    simTime(),
    duration);
```

The jammer power is converted from Watts to milliwatts:

```cpp
double power_mW = power * 1000.0;
```

because VEINS internally represents signal power in mW.

The jammer occupies the selected IEEE 802.11p frequency and adjacent bands:

```cpp
signal.at(freqIndex - 1) = power_mW;
signal.at(freqIndex) = power_mW;
signal.at(freqIndex + 1) = power_mW;
```

The signal boundaries are configured:

```cpp
signal.setDataStart(freqIndex - 1);
signal.setDataEnd(freqIndex + 1);
signal.setCenterFrequencyIndex(freqIndex);
```

Finally, the signal is attached to the frame:

```cpp
frame->setSignal(signal);
frame->setDuration(duration);
```

---

# Sending the Interference Frame

The completed frame is transmitted through the standard VEINS channel:

```cpp
sendMessageDown(frame.release());
```

After this operation, the jamming signal follows the normal VEINS communication pipeline:

* channel propagation;
* antenna gain calculation;
* path loss;
* obstacle shadowing;
* interference evaluation;
* receiver decoding.

Therefore, the jammer affects vehicles and RSUs exactly as a real physical interference source would.

---

# Complete Reactive Jamming Workflow

The complete execution sequence is:

1. A legitimate IEEE 802.11p transmission starts.
2. `BasePhyLayer::handleAirFrameStartReceive()` detects the incoming frame.
3. The PHY layer emits `incomingFrame`.
4. `JammerApplication` receives the signal.
5. The application checks whether the jammer is enabled and idle.
6. The application calls `PhyLayer80211p::startJamming()`.
7. The PHY layer creates an artificial IEEE 802.11p interference frame.
8. The frame is injected into the wireless channel.
9. After `jammingDuration`, the timer stops the attack.
10. The jammer returns to the idle state.

---

# Design Summary

The implementation follows three main principles:

### PHY-aware detection

The jammer reacts to real wireless activity detected at the physical layer instead of relying on application or MAC events.

### Separation of responsibilities

The application decides **when** to attack, while the PHY layer defines **how** interference is generated.

### VEINS compatibility

The jammer reuses the existing VEINS wireless channel, propagation models, antenna models, and interference calculations.
