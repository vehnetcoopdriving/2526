# Implementation

## Overview

The reactive jammer is implemented as an application-layer module built on top of the standard **VEINS 5.3.1** framework. Instead of modifying the communication stack, the project extends the existing RSU application, allowing the jammer to integrate seamlessly with the default IEEE 802.11p architecture.

The implementation is organized into a small set of files:

| File                    | Purpose                                                                     |
| ----------------------- | --------------------------------------------------------------------------- |
| `JammerScenario.ned`    | Extends the original VEINS scenario by adding a jammer node.                |
| `JammerApplication.ned` | Declares the jammer module and its configurable parameters.                 |
| `JammerApplication.h`   | Defines the application interface, timers, state variables, and statistics. |
| `JammerApplication.cc`  | Implements the reactive jamming logic and statistics collection.            |
| `omnetpp.ini`           | Configures the simulation, including jammer position and attack parameters. |

This structure keeps the implementation modular and makes it easy to reuse the jammer in different VEINS scenarios.

---

## Jammer Node

The jammer is implemented as a stationary RSU using the standard VEINS IEEE 802.11p protocol stack. The only customized component is the application layer, which is replaced by `JammerApplication`.

As a result, the jammer behaves like any other network node and can transmit packets through the existing communication stack without requiring modifications to the VEINS framework.

---

## Jammer Application

`JammerApplication` extends `DemoBaseApplLayer` and is responsible for controlling the attack.

During initialization, the application:

* loads the configuration parameters from `omnetpp.ini`;
* creates the timers used to schedule jamming events;
* obtains a reference to the IEEE 802.11p MAC layer;
* subscribes to channel busy notifications;
* initializes the statistics collected during the simulation.

After initialization, the application remains idle until wireless activity is detected.

---

## Channel Activity Detection

Instead of inspecting every received packet, the jammer listens to the `sigChannelBusy` signal generated by the IEEE 802.11p MAC layer.

Whenever the channel changes from idle to busy, the application is notified and schedules a jamming transmission after the configured reaction delay.

Using MAC-layer notifications provides an efficient solution while preserving full compatibility with the original VEINS implementation.

---

## Interference Transmission

When activated, the jammer generates a broadcast IEEE 1609.4 frame and transmits it on the Control Channel (CCH).

The transmission is performed through the standard VEINS communication stack using the inherited `sendDown()` function. The frame is transmitted for the configured jamming duration before the application returns to the idle state.

Both the reaction delay and the transmission duration are configurable through `omnetpp.ini`.

---

## Configuration

All attack parameters are defined in `omnetpp.ini`, allowing different experiments to be performed without recompiling the project.

| Parameter         | Description                                               |
| ----------------- | --------------------------------------------------------- |
| `enabled`         | Enables or disables the jammer.                           |
| `reactionDelay`   | Delay between channel detection and jamming transmission. |
| `jammingDuration` | Duration of each interference burst.                      |
| `jammingPower`    | Transmission power of the jammer.                         |

---

## Statistics

During each simulation, the jammer records several metrics describing its activity, including:

* detected channel activities;
* jammer activations;
* configured attack parameters.

These statistics are exported as OMNeT++ scalar results and can be analysed using the standard result analysis tools.

---

## Compatibility with VEINS Applications

The original `TraCIDemo11p` and `TraCIDemoRSU11p` applications were slightly modified to correctly handle jammer-generated packets.

Both applications originally assumed that every received frame was a `TraCIDemo11pMessage`. Since the jammer transmits generic IEEE 1609.4 frames, a simple type check was added before processing received packets.

This modification prevents invalid casts while leaving the original communication and forwarding behaviour unchanged.

---

## Design Summary

The implementation follows a modular design based on three principles:

* **Modularity** – the jammer is implemented as a separate application module.
* **Configurability** – all attack parameters are defined in `omnetpp.ini`.
* **Compatibility** – the solution integrates with VEINS 5.3.1 without modifying the framework itself.

This design also makes it straightforward to implement alternative jamming strategies by extending the application logic.
