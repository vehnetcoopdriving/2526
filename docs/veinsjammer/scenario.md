# Scenario

## Network Setup

The implemented scenario is based on the **VEINS 5.3.1** RSU example and models a Vehicular Ad Hoc Network (VANET) operating with the IEEE 802.11p communication standard. Vehicle mobility is managed by **SUMO**, while network communication is simulated in **OMNeT++** using the VEINS framework.

The network consists of three main types of nodes:

* **Vehicles**, dynamically created and controlled through the TraCI interface.
* **Road Side Units (RSUs)**, deployed at fixed positions to provide infrastructure-based communication.
* **Reactive jammer**, implemented as an additional stationary node equipped with the same IEEE 802.11p communication stack as the RSUs.

The simulation area is configured as a **3200 m × 3200 m** playground with a maximum communication/interference distance of **2600 m**. The default RSU is located at **(2000 m, 2000 m, 3 m)**. Two jammer placement scenarios are considered: a **near** scenario, in which the jammer is positioned at **(2050 m, 2050 m, 3 m)** close to the main communication area, and a **far** scenario, in which the jammer is positioned at **(1400 m, 1400 m, 3 m)**, increasing its distance from the communicating vehicles and the RSU. This allows the impact of jammer location on communication performance to be evaluated.

All wireless nodes use the IEEE 802.11p protocol stack provided by VEINS with the following configuration:

* transmission power: **20 mW**;
* bitrate: **6 Mbps**;
* Control Channel (CCH) communication;
* propagation delay enabled;
* obstacle shadowing model enabled;
* antenna model defined in `antenna.xml`;
* background noise floor set to **−98 dBm**.

Vehicle applications are based on the standard `TraCIDemo11p` application, while RSUs use `TraCIDemoRSU11p`. Beacon transmission is disabled by default, although additional configurations included in `omnetpp.ini` allow beaconing and service channel switching to be enabled for further experiments.

The simulation runs for **200 seconds**, during which SUMO continuously updates the position of all vehicles through the TraCI interface.

## Attack Model

The implemented attacker follows a **reactive jamming** strategy.

Unlike a constant jammer, which continuously occupies the wireless medium, a reactive jammer remains silent until it detects legitimate channel activity. This behaviour reduces unnecessary transmissions while concentrating interference on active communications.

The jammer subscribes to the `sigChannelBusy` signal generated by the IEEE 802.11p MAC layer. Whenever the MAC reports that the wireless channel has become busy, the jammer schedules a transmission after a configurable reaction delay.

The attack proceeds as follows:

1. A legitimate node starts transmitting.
2. The MAC layer reports that the channel is busy.
3. The jammer detects the event.
4. After the configured reaction delay, the jammer generates an interference frame.
5. The interference burst is transmitted for the configured duration.
6. The jammer stops transmitting and waits for the next channel activity.

The interference packet is transmitted as a broadcast IEEE 1609.4 frame on the Control Channel (CCH). Since the jammer uses the same physical and MAC layers as legitimate nodes, its transmissions are handled by the standard VEINS communication stack, making the attack behaviour consistent with the simulator architecture.

The jammer behaviour is fully configurable through the simulation configuration file. The principal attack parameters are summarized below.

| Parameter         |    Value | Description                                           |
| ----------------- | -------: | ----------------------------------------------------- |
| `enabled`         |   `true` | Enables or disables the jammer.                       |
| `reactionDelay`   | `0.01 s` | Time between channel detection and jammer activation. |
| `jammingDuration` | `0.02 s` | Duration of each interference burst.                  |
| `jammingPower`    |  `20 mW` | Transmission power used by the jammer.                |

The jammer records several runtime metrics, including the number of detected transmissions, the number of jamming activations, and timing information related to each attack. These statistics are used to evaluate the effectiveness and behaviour of the implemented reactive jamming strategy during simulation.
