# Scenario

## Network Setup

The project extends the standard **VEINS 5.3.1** RSU example to simulate a Vehicular Ad Hoc Network (VANET) based on the IEEE 802.11p communication standard. Vehicle mobility is handled by **SUMO**, while network communication is simulated in **OMNeT++** using the VEINS framework.

The network includes three types of nodes:

- **Vehicles**, created dynamically through the TraCI interface.
- **Road Side Units (RSUs)**, placed at fixed locations.
- **Reactive jammer**, implemented as an additional stationary RSU with a custom application.

The simulation area is **3200 m × 3200 m**, with a maximum communication/interference range of **2600 m**. The legitimate RSU is located at **(2000 m, 2000 m, 3 m)**.

Two jammer placements are evaluated:

- **Near scenario:** **(2050 m, 2050 m, 3 m)**, close to the RSU and vehicles.
- **Far scenario:** **(1400 m, 1400 m, 3 m)**, farther from the main communication area.

Comparing these two configurations allows the effect of jammer location on network performance to be evaluated.

All wireless nodes use the standard VEINS IEEE 802.11p protocol stack with the following settings:

- transmission power: **20 mW**;
- bitrate: **6 Mbps**;
- Control Channel (CCH);
- propagation delay enabled;
- obstacle shadowing enabled;
- antenna model defined in `antenna.xml`;
- background noise floor: **−98 dBm**.

Vehicles run the standard `TraCIDemo11p` application, while RSUs use `TraCIDemoRSU11p`. Beaconing is disabled by default, although additional configurations in `omnetpp.ini` allow beacon transmission and channel switching to be enabled.

Each simulation runs for **200 seconds**, during which vehicle positions are continuously updated through TraCI.

## Attack Model

The attacker implements a **reactive jamming** strategy.

Instead of transmitting continuously, the jammer remains idle until it detects activity on the wireless channel. When a transmission is detected, it waits for a configurable reaction delay before sending a short interference burst.

The jammer monitors channel activity by subscribing to the `sigChannelBusy` signal generated by the IEEE 802.11p MAC layer.

The attack sequence is:

1. A legitimate node starts transmitting.
2. The MAC layer reports that the channel is busy.
3. The jammer detects the event.
4. After the configured reaction delay, it transmits an interference frame.
5. The transmission lasts for the configured jamming duration.
6. The jammer returns to the idle state.

The interference frame is sent as a broadcast IEEE 1609.4 packet on the Control Channel (CCH). Since the jammer uses the standard VEINS communication stack, its transmissions are handled like those of any other network node.

## Configuration Parameters

The jammer behavior is controlled through `omnetpp.ini`.

| Parameter | Value | Description |
|-----------|------:|-------------|
| `enabled` | `true` | Enables or disables the jammer. |
| `reactionDelay` | `0.01 s` | Delay before starting the interference transmission. |
| `jammingDuration` | `0.02 s` | Duration of each interference burst. |
| `jammingPower` | `20 mW` | Transmission power used by the jammer. |

Changing these parameters makes it possible to evaluate different attack configurations without modifying the source code.

---

## Collected Statistics

During each simulation, the jammer records several metrics, including:

- number of detected channel activities;
- number of jamming activations;
- activation timing information.

These statistics are used to evaluate the behavior and effectiveness of the reactive jamming strategy under different simulation scenarios.
